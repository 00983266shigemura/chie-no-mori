## 3. MORPHOLOGY｜対象の識別性を確保する

### 3.1 制作前の形態設計

44点の制作前に、対象ごとの内部仕様表を作成する。

各対象について、次を定義する。

- 日本語名
- 分類
- 代表的な成虫の姿
- 描画する性別
- 識別に重要な特徴（1〜3点）
- 角・大あご・頭部・胸部・上翅の特徴
- 脚・触角の特徴
- 代表的な体色・模様
- 類似種との違い
- 形態情報の確認状況

必要な場合は、博物館・大学・研究機関・信頼できる昆虫図鑑などの資料を参照する。

参照画像をそのまま複製・トレースすることは禁止する。特徴を理解したうえで、独自の簡略イラストに再構成する。

資料を確認できない場合は、既知の形態情報から制作できる範囲を判断し、推測箇所を記録する。

確認できていない情報を「確認済み」としない。

### 3.2 性別と個体差

- カブトムシのなかま：原則として、種の特徴が明瞭な成虫の雄。

- そのほかの甲虫：代表的な成虫の姿。必要な場合は性別を指定する。

角や大あごの本数・位置・形は、対象の実際の特徴に従う。

特徴を強調するための適度なデフォルメは許可するが、実在しない角や突起を追加しない。

### 3.3 名称が曖昧な対象

不確かな対象を、確認済みの特定種として扱わない。

## 4. DESIGN SYSTEM｜44枚共通の描画仕様

### 4.1 ファイル仕様

- 形式：PNG
- 解像度：512×512px
- カラーモード：RGB
- 背景：純白（#FFFFFF）
- 透明度：なし
- 画像内の対象：1ファイルにつき1対象
- ファイル名：第5節の指定どおり

### 4.2 構図

- 背中側を真上から見た図鑑標本のような姿。
- 頭を上、尾端を下に配置。
- 体軸は原則として垂直。
- 脚は左右に自然に広げる。
- 触角は形態的特徴が分かるように配置。
- 原則として左右対称。ただし、実際の形態の正確性を優先する。
- 真横・正面・斜め視点は禁止。
- 影・床・葉・木・石などの環境要素を描かない。

角や大あごの形は、背面視点で分かる範囲で正確に表現する。

### 4.3 対象の大きさ

- 角・大あご・脚・触角を含む対象全体の最長辺が、おおむね画面の75〜85%。
- 画面の中央付近に配置。
- 全部位が画面内に収まり、切れないこと。
- 対象同士の実物の大きさの違いは表現しない。
- 体型・角・あごの自然な比率は維持する。

角の長い甲虫でも、角だけが巨大になり体が不自然に小さくならないようにする。

### 4.4 線

- 外側の輪郭線：黒、512px換算で約9px。
- 内側の構造線：外側より細く、原則4〜5px。
- 原則として全44点で線幅ルールを共通化。
- 輪郭線は明瞭で、途切れや二重線を避ける。
- 必要に応じて曲線を使い、子どもが見分けやすい形にする。

### 4.5 色・塗り

- フラットな単色塗り。
- グラデーション・陰影・光沢表現・写真風テクスチャは禁止。
- 1枚あたりの使用色は必要最小限とし、おおむね8色以内。
- 実物が単色に近い場合、無理に色を増やさない。
- 黒や濃褐色の甲虫も、輪郭と部位の境界を識別できる明度に調整する。
- ニジイロクワガタ・ヤマトタマムシなどは、複数の明快な色面によって特徴的な色彩を表現してよい。
- 実際の特徴と異なる派手な着色は禁止。

### 4.6 禁止事項

画像内に以下を入れない。

- 文字、数字、ファイル名
- ロゴ、透かし
- 顔の表情や擬人化
- 吹き出し
- 枠線、額縁
- 装飾
- 背景の物体
- 複数の甲虫
- 同じ甲虫の別視点

### 4.7 統一性の設計

共通ルールは「視点・配置・線・塗り・背景・余白」とする。

一方で、体型・角・あご・脚・触角は対象ごとに変える。

最初のヘラクレスオオカブトを色や形の共通テンプレートにはしない。

カブトムシ・クワガタ・その他の甲虫について、それぞれの形態に適した構造を使用しつつ、描画スタイルは完全に共通化する。

### 各バッチの処理

2. 各対象を独立したイラストとして描画する。
3. 共通描画仕様に合わせて512×512 PNGにする。

5. 保存ファイルを再読み込みする。
6. 自動品質検査を行う。
7. 実際の画像を確認し、形態とスタイルを検査する。
8. 不合格画像だけを修正する。
9. 合格済みファイルと検査結果をチェックポイントに記録する。
10. 次のバッチへ進む。

バッチ間のユーザー確認は不要。

### 再開・重複実行防止

- 完成済みファイルを無条件に再生成しない。

- ファイルが存在するだけで合格とは判断しない。

## 7. QUALITY ASSURANCE｜検証基準

### 7.1 自動検査

Python等で次を検証する。

| 検査項目    | 合格条件              |
| ------- | ----------------- |
| ファイル数   | 指定44点が存在する        |
| ファイル名   | 指定リストと完全一致        |
| 余分なPNG  | 0件                |
| 重複ファイル名 | 0件                |
| 画像形式    | 全件PNG             |
| 解像度     | 全件512×512         |
| カラーモード  | 全件RGB             |
| 透明度     | 全件なし              |
| 背景      | 外周が白              |
| 破損      | 全件正常にデコードできる      |
| 配置      | 対象が中央付近にある        |
| サイズ比率   | 対象全体の最長辺が原則75〜85% |
| はみ出し    | 対象が画像端で切れていない     |
| ZIP     | 全件を収録し再読み込みできる    |

Pillowなどを使用して画像の読み込み、ピクセル情報、背景、外接矩形を確認する。

画像のサイズ・背景・主対象の外接矩形は、可能な範囲で定量検査する。

複雑な角や脚、背景と同色の部分などにより自動判定が不正確になる場合は、視覚検査で補完する。

### 7.2 視覚検査：統一性

全44点のコンタクトシートを作成し、次を確認する。

- 背面から見た視点が共通
- 頭の向きが共通
- 余白と配置が共通
- 輪郭線の太さが共通
- 塗り方が共通
- 背景が共通
- イラストの詳細度が大きく異ならない
- 他の画像と比較して極端に小さい・大きいものがない

異常があれば、該当ファイルだけを再検査・修正する。

### 7.3 視覚検査：識別性

各画像について、対象名と形態が一致するかを確認する。

特に以下を検査する。

- 角の本数・位置・形状
- 大あごの長さ・曲がり方・歯の形
- 頭部と胸部の形
- 上翅の輪郭・色・模様
- 脚と触角
- 類似対象との違い
- 幼児向けとして十分な明瞭さ

色や模様だけを変えた使い回しでは、種の識別性を合格にしない。

### 7.4 検査結果の区分

各ファイルの結果を次の3状態で管理する。

- PASS：必要な検査に合格
- FAIL：具体的な不適合がある
- UNVERIFIED：必要な検査を実施できていない、または確信が持てない

自動検査に合格しても、視覚検査が未実施なら総合PASSにしない。

種の識別性は、可能な場合に信頼できる形態資料と比較する。

AI自身による目視評価だけで、専門家による分類学的な同定まで保証したことにはしない。

### 7.5 修正ルール

FAILの画像は原因を特定し、修正する。

- 技術的な問題：サイズ・背景・ファイル形式などを修正。
- スタイル上の問題：共通デザインに合わせて修正。
- 形態の問題：角・あご・体型・模様などを修正。

修正後は該当ファイルの自動検査と視覚検査を再実施する。

検証不能な項目が残る場合は、UNVERIFIEDとして記録する。

第5節の指定どおり、44点の個別PNGを格納する。

### 8.2 contact_sheet.png

各画像の下に次のラベルを付けてよい。

- 日本語名

全体の統一性を比較できる十分な解像度で作成する。

### 8.3 manifest.csv

44対象について、次の情報を記録する。

- no
- filename
- japanese_name
- category
- generation_method
- file_status
- automated_validation
- visual_consistency
- morphology_validation
- overall_status
- sha256
- notes

検証が未実施の場合は空欄やPASSにせず、UNVERIFIEDを明記する。

日本語文字列がExcel等で文字化けしにくいよう、UTF-8 BOM付きCSVとする。

### 8.4 ZIPの最終検査

- ZIP作成後、別途再オープンして構造を確認する。
- 全44ファイルが期待したパスにあること。
- 同名ファイルが重複していないこと。
- ZIP内のPNGを読み込み、画像破損がないこと。
- manifestの記録と実ファイルが一致すること。
- SHA-256が保存時の記録と一致すること。

ZIPを作成しただけでは完了にしない。

## 9. CHECKPOINT｜中断時の処理

途中で実行が続行できなくなった場合でも、完成済み成果物を失わないようにする。

### 9.1 チェックポイント

バッチの終了時に以下を保持する。

- 完成済みファイル
- 未完成ファイル
- ファイルごとの検査状況
- 完成済みファイルのSHA-256
- 次に制作する対象番号
- 使用した制作方式
- 共通描画仕様
- 再開に必要な情報

### 9.2 部分納品

途中停止時には、利用可能な完成済みPNGと検査結果を収録した部分納品ZIPを作る。

ZIPには `resume_state.json` も格納し、少なくとも次を記録する。

- 完成済みの対象番号とファイル名
- 未完成の対象番号とファイル名
- 検査済み・未検査の区別
- 次回の開始位置
- 再開時に守る描画仕様

部分納品ZIPに未完成ファイルを完成品として混入させない。

途中停止の原因が画像生成ツールの応答仕様、実行環境、利用上限などの場合は、実際に確認できた範囲でその理由を記録する。

チェックポイントが次の会話で自動的に引き継がれるとは仮定しない。再開に必要な情報は部分納品ファイルへ格納する。

## 10. COMPLETION GATE｜完了条件

以下の条件をすべて満たした場合のみ「44点完成」と報告する。

1. 指定44ファイルが実際に存在する。
2. ファイル名がすべて一致する。
3. 自動検査が44点すべてPASS。
4. 視覚検査で明白な統一性の欠陥がない。
5. 対象名と形態の重大な不一致がない。
6. 44点の総合品質に重大な未確認事項が残っていない。
7. コンタクトシートが生成されている。
8. manifest.csvが44行存在し、実ファイルと整合している。
9. ZIP作成・再読み込み・内容検査が成功している。
10. 実在するZIPのダウンロードリンクを提示できる。

完了条件を満たせない場合は、完成済み件数と未完了件数を正確に報告する。

**未検証を合格とせず、実ファイルが存在しない状態を納品完了としない。**

## 11. FINAL REPORT｜最終回答

作業中の細かな説明は最小限にし、制作・保存・検証を優先する。

最終回答は原則として次の4項目だけとする。

1. **完了点数**：XX/44
2. **自動検査**：PASS件数・FAIL件数・UNVERIFIED件数
3. **視覚検査**：統一性・識別性の結果、重大な不適合と未確認事項
4. **納品**：実際に作成したZIPのダウンロードリンク

44点完成できなかった場合は、この4項目に加えて未完成ファイル名、停止理由、部分納品ZIPと再開情報を示す。

確認質問やバッチごとの途中承認を求めず、可能な限り全44点の完成まで自動継続する。
